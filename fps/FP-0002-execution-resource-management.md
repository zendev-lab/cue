# FP-0002: 执行级资源管理

## 摘要

Cue 以一次执行（Execution）为单位管理资源：开始前一次性申请，所有步骤共享同一批
分配，直到执行结束且物理进程全部退出后释放。多步骤任务因此可以持续使用同一组 GPU，
并发任务则由统一的资源服务协调，避免重复分配。

资源服务由 cued 的 Composition 承载，支持 NVIDIA GPU/显存和通用资源 provider。
资源策略不进入 Core 或 ExecutionPlan，遵循
[FP-0001](FP-0001-structured-execution-kernel.md) 的语义与物理实现分离原则。

## 动机

训练任务通常包含准备、训练和结果处理。用户希望一次声明所需设备与容量，整个流程就能
稳定使用这些资源，而不必在步骤之间重新竞争设备，或让每个客户端自行协调占用。

资源管理应回答三个问题：任务何时可以开始、执行期间哪些资源归它使用、何时能够安全
交给下一个任务。客户端断开、取消、provider 故障和 daemon 重启都不应让这些归属失去
依据。用户也需要直接看到任务在等待什么、获得了什么，以及哪些占用仍待清理。

## 设计

### 一次声明，整个执行共享

资源需求通过提交参数声明：

```shell
cue run train.cue --need gpu=2 --need gpu_mem=24GiB
cue client run train.cue --need gpu=2 --need gpu_mem=24GiB
cue client exec --need gpu=1 -- python train.py
```

`run` 接受文件路径前后的 `--need KEY=QUANTITY`；`exec` 在 `--` 前解析提交选项，
之后按 exec SOURCE 规则处理命令。资源数量支持整数计数和字节单位；重复键、未知键、
类型错误、空值、非正数和溢出在创建执行前拒绝。

`gpu` 表示设备数，`gpu_mem` 表示每张卡的显存需求。只声明显存时申请一张卡，只声明
设备数时独占设备，两者同时声明时按显存预算允许共享。显存预算用于准入，不是对程序
实际显存分配的硬限制。

同一执行的顺序步骤、并行分支、pipeline 和 PTY 共享整批分配。步骤之间不释放资源，
并行分支不重复获得预算或自动切分设备。需要独立配额的工作分别提交为独立执行。

### 统一准入，明确等待原因

组合服务统一持有 provider registry、资源占用和可取消的队列。每个资源键只有一个
provider，重复 provider ID 或键归属属于配置错误。

执行、资源需求、入队顺序和提交去重结果原子持久化；同一逻辑提交重放返回原执行，
不重复入队或申请。资源全部就绪前不驱动任何执行步骤，包括 Builtin，但取消与清理
不受准入阻塞。取消和分配竞态不能导致取消后新启动进程。

容量不足时按入队顺序寻找最早可满足的请求，允许后续任务先运行。不声明资源的执行
不进入队列。释放、provider 恢复和有界周期探测触发重试；该策略优先利用可用资源，
不保证大请求无饥饿。

跨 provider 按稳定 ID 顺序申请，全部成功并持久化后才开始执行。部分失败时逆序释放，
不能长期持有部分分配等待其他资源。回滚未确认时保留占用并继续清理，不能带着残留申请
重新排队。容量不足、非法需求和 provider 故障分别报告，不把故障伪装成等待容量。

### 物理分配不改变执行语义

资源需求和占用以 Execution ID 关联，由组合服务持久化，不扩展内核执行状态。
分配结果通过物理 SpawnContext 应用于各个 Run，逻辑 Scope、argv 和 EnvPatch 保持不变。

资源服务管理设备环境变量，例如 `CUDA_VISIBLE_DEVICES` 和 `CUDA_DEVICE_ORDER`。
这些覆盖在逻辑环境构造后应用，步骤中的 env set/unset 不能改变所分配的设备。
多个 provider 贡献同一环境键时拒绝冲突，不按执行顺序静默覆盖。

### 归属持续到安全释放

执行正常结束、失败或取消后，必须确认所有已启动的物理执行均已静止，才能释放资源。
客户端断开不改变资源归属；单个步骤结束或数据库中的执行终态也不能单独作为释放依据。
没有启动物理进程的已取消执行可以直接清理分配。

服务持久化稳定申请 ID、各 provider 的 grant、设备身份和清理进度。调用 provider 前
先记录申请身份，响应丢失后查询原申请，不换 ID 重试。只有确认原申请已无占用，才允许
开始新的申请尝试。

释放是幂等操作。失败或结果不明时保留占用与错误，后台重试；执行结果和资源清理状态
分别展示，清理失败不改写程序退出码。完成记录的重试不能重新启动进程或重复申请资源。

恢复时先核对持久化申请与 provider，再允许执行或重新准入。无法确认物理执行所有权
或申请结果时保留隔离占用并报告相关执行和申请身份，阻止不安全的恢复。不能仅凭 PID
消失、超时或执行终态回收资源，也不能清空账本来绕过未知占用。

### 可扩展的资源提供者

通用 JSON stdio provider 提供版本化的 probe、reserve、lookup、release 操作。
申请携带 daemon 持久身份、稳定申请 ID、Execution ID 和需求；结果提供 grant 身份、
分配信息及物理环境贡献。

相同身份和参数的申请返回同一结果，参数不同则拒绝。查询区分已分配、已释放、确定
未申请和结果未知；释放可重复且结果可查。provider 负责资源分配的串行化与持久去重，
不能依赖单次 CLI 进程的内存。调用必须有界，超时、进程失败和畸形响应作为故障报告。

NVIDIA provider 结合 NVML 实时探测与持久化预留，区分物理空闲和 Cue 预算，避免重复
扣减同一用量。分配绑定稳定设备身份，重启后不凭设备序号重新解释归属。无驱动或设备时
普通执行与其他 provider 仍可用，GPU 请求明确报告不可用原因。

### 可观察、可取消

`cue resources` 展示容量、分配、等待执行、阻塞原因和清理状态；`cue providers`
展示 provider 身份、资源键及可用性。两者支持 JSON，查询不创建执行或触发申请。
`cue client show` 同时展示执行状态和关联的资源状态。

等待中的任务已有 Execution ID，可通过 cancel/kill 取消；CLI 保持执行等待及退出码
约定，输入或提交错误返回非零。资源状态区分等待、申请中、已分配、清理中、已释放和
结果不明，避免把“程序结束”误读为“资源已可重新分配”。

范围限定为单一 daemon 协调的本地资源。跨 daemon 协调、多机调度、抢占、CPU/内存
硬限制、孤儿进程接管及 TUI 资源专页不在本提案范围内。

## 兼容性

资源需求与查询需要扩展 daemon 协议，并升级协议版本；官方 CLI/client/daemon 同步
升级，版本不匹配在握手时拒绝。

需求属于整个执行，不增加文件级声明。Step 级 `:run(need.*)` 返回迁移提示，要求将
需求移至提交参数；需要各步骤不同配额时拆分执行，不隐式提升或重新分配资源。
不导入 v3 资源状态或兼容旧 provider 协议。

资源账本和执行存储同事务迁移。升级前停止 daemon 并确认无未解决的物理执行；降级前
完成资源清理，再恢复升级前备份，不能让旧 daemon 打开包含未清理占用的新存储。

## 验证

- 多客户端竞争不超分；顺序步骤固定设备，并行分支共享预算；pipeline 和 PTY 使用
  相同分配，环境变更不能绕过设备约束。
- 验证最早可满足请求先运行、无需求任务不受阻塞，以及等待取消和申请成功的竞态。
- 注入多 provider 部分失败、回滚失败与响应丢失，验证幂等身份、查询恢复和占用可见性。
- 在提交、申请、进程退出和释放的边界注入崩溃，验证不重复启动、不提前回收，未知
  物理所有权阻止恢复，执行退出码与资源清理状态独立。
- 使用真实 CLI 和隔离 daemon 验证参数、JSON、退出码、迁移提示、握手和只读查询；
  断开提交客户端后仍可查询与取消任务。
- 使用可控 GPU 探测验证预算、独占与设备身份恢复，并在 NVIDIA 实机验证设备注入、
  实时占用和完整释放。
