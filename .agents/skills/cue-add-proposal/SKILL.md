# Cue 提案写作

让公开契约及其取舍可以评审，按当前请求交付判断、审阅意见或提案文本。
提案写作本身不授权实现、采纳或发布。

## 核对现状与提案门槛

先读 [FP-0000](../../../fps/FP-0000-governance.md)、
[提交指南](../../../fps/README.md)、[协作约定](../../../AGENTS.md) 和
[贡献指南](../../../CONTRIBUTING.md)，再读相关 FP、实现、调用方及测试。
区分正在运行的行为、已有设计与尚未实现的目标。

按 FP-0000 判断是否涉及新的公开契约或治理决定；不能用其他仓库的“大影响”门槛
豁免本仓库要求的 FP。恢复既有契约的缺陷修复及既定设计的实现沿用已有决定。
说明走直接修改、已有 FP 还是新 FP，以及决定性依据；仅评估或审阅时不创建文件。

## 调研并取得关键选择

从实际源码和测试核实问题，涉及外部方案时查一手文档、源码或论文，并记录版本及
证据缺口。围绕公开行为、Core 与 Composition 的责任、状态归属、兼容迁移及恢复
比较可行方案，适用时包含维持现状，说明推荐与代价。

在定案前实际询问尚未决定的关键选项。起草请求不等于已选择设计；已有用户选择、
适用 FP 或明确委托可以复用，记录其依据，不重复询问。普通可逆细节自行解决。
等待时继续独立调研或不受影响的章节；无回复不表示同意，不能实现依赖未决选项的行为。

## 编写和修订

使用[现有模板](../../../templates/fp.md)，按
[配置](../../../proposal.toml)与 [schema](../../../schemas/fp.schema.json)
填写元数据。编号前核对当前文件和远端提案 PR；候选直接放入 fps，不新增草稿目录
或采纳状态字段。作者、日期和引用来自实际证据，不复制模板占位值或其他仓库格式。

在既有章节说明问题证据、拟议行为、选择及其来源、放弃方案的理由、兼容影响和
可观察验收条件。正文和标题按本仓库使用中文，保留代码与技术标识的准确写法。
同一概念沿用已有 FP 的首选术语和定义；术语声明与关系格式遵循本仓库配置。

写清执行者、对象、条件范围、否定、时序、计数与失败边界。缺失语义保留为待决问题，
不能为简化句子补造重试次数、超时或保证。区分规范要求、建议、拟议行为与实测事实；
论证用连贯段落，有顺序的操作才写成步骤。

编辑修订保留标识与历史；实质改变决定时按 FP-0000 处理替代关系。合入 FP 只保存
提案文本，不证明采纳、排期或实现。实现修改交给本仓库运行时变更流程，分别评审。

## 校验与交付

按贡献指南运行只读检查；修改了提案或元数据时，使用现有工具更新索引，检查完整 diff
并再次校验，不手改索引或修复无关记录。缺少工具或未解决的设计选择应明确报告。
结构通过不证明方案正确或已被接受。

交付提案门槛判断、文档或审阅意见、关键决定来源、实际检查及未决问题。Git 交付遵循
用户终点和仓库流程，不因载入 skill 新增发布权限或重复索要已有授权。
