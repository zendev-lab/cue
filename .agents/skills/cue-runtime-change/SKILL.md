# Cue 运行时变更

把观察到的问题定位到拥有该语义的层，再验证生产调用路径与失败恢复。
仅诊断请求止于证据和修复方向；已有修复授权时继续完成相应实现与验证。

## 确定契约与责任层

按 [协作约定](../../../AGENTS.md) 阅读相关 FP，再对照
[架构](../../../ARCHITECTURE.md)、[设计入口](../../../docs/design/README.md)
和当前代码。区分已实现行为、提案中的要求以及尚未实现的能力。

沿实际路径查找负责的层：语言编译、typed ExecutionSpec、协议校验、
Core reducer、持久化、运行时 provider、daemon 组合、客户端结果展示。
Core 决定执行语义；物理进程或存储机制不能在另一层重新解释计划与 Scope。
通过当前类型和调用点核实所有权，不依据旧版本中的名称迁移实现。

改变公开契约时按 [FP-0000](../../../fps/FP-0000-governance.md) 选择流程；
恢复既有契约的修复、测试和开发指导沿用现有规则，不另造提案要求。
不要把其他仓库的提案阈值、协议版本或兼容策略当作 Cue 的当前契约。

## 固定可复现的现场

记录源码 revision、实际二进制路径、客户端与 daemon 身份、socket、数据库
以及握手结果。替换磁盘上的 cued 不会替换已经运行的进程。
先确认通信双方版本，再判断失败来自请求、协议、状态转移还是物理执行。

进程测试复用仓库现有 fixture，为实例同时分配独立 socket 和数据库，
显式设置 CUE_SOCKET，并限制等待和清理范围。只清理本次 fixture 创建的
进程与数据，不对用户 daemon 执行停止、重启或删除数据库来复现问题。
不要因为连接失败就假定服务未启动，也不要把另一个实例的响应当成本次启动成功。

## 验证转移与副作用

从最后一个已确认的事实追到第一个缺失、重复或错误的结果。按改动选择
能推翻假设的用例，不为每次修改机械跑全部故障场景：

- 计划或 Scope：在 Core 层断言结果聚合、Step 身份和 Scope 传播；
  编译成功不能证明执行语义正确。
- 协议或幂等：沿实际编码、解码、校验和消费者验证；区分请求身份与
  副作用身份，检查重复请求及响应丢失。收到请求不等于操作已经提交。
- 持久化或恢复：通过真实 SQLite fixture 检查提交、重开和故障状态；
  崩溃后未知的物理执行结果不能靠自动重放或伪造完成来消除。
- 启停或取消：观察 readiness、拥有的子进程退出、资源释放以及后续重启；
  发出信号或取消请求不能证明已完成回收。
- CLI 或 PTY：运行真实命令，检查 stdout、stderr、退出码与终端行为。
  客户端退出与执行取消是不同事件；不要用纯 reducer 测试替代进程边界。

测试应控制竞争事件发生的边界并保留必要的真实进程或存储。
固定 sleep、额外重试和更长超时不能代替握手、事件或资源状态证据。
Linux 专属机制在 macOS 上没有执行时，明确保留验证缺口。

## 选择现有测试入口

[测试规范](../../../docs/testing.md) 拥有测试层次，
[贡献指南](../../../CONTRIBUTING.md) 和 [justfile](../../../justfile)
拥有检查命令。优先扩展现有用例：

- [daemon 生命周期](../../../crates/cue-daemon/tests/lifecycle.rs)：
  readiness、竞争启动、数据库所有权和 drain。
- [控制与恢复](../../../crates/cue-daemon/tests/control_recovery.rs)：
  不兼容 listener、握手超时、信号与未知控制结果。
- [CLI 用户流程](../../../crates/cue-cli/tests/user_workflows.rs)：
  实际命令的失败信息、输出和退出行为。

例如，生命周期用例可通过
`cargo test -p cue-daemon --test lifecycle` 定向执行，再按贡献指南完成所需门禁。
源码二进制通过不代表发行包安装通过；产品 Skill 的分发仍由
[skills/cue](../../../skills/cue/SKILL.md) 与 npm package smoke 负责，
本开发 Skill 不进入那个产品指导入口。

报告复现条件、契约所有者、证明或排除的原因、实际验证与未覆盖平台。
不要以提案合入、单次握手成功或测试跳过代替运行时验收。
